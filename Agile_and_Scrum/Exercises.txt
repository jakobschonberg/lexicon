1.1
With the waterfall method, no feedback or little feedback is recieved before the final product is shipped.
Which could either mean you develop features that were not needed and or the final product doesn't meet the needs.
Mistakes are discovered late, meaning correcting mistakes is more costly.

1.2
* Working software over comprehensive documentation:
    Make sure your code works before writing comprehensive documentation.
    Comment your code when it feels needed, but don't overdo the documentation part (especially when your code isn't final yet).

* Responding to change over following a plan.
    When developing a feature, new problems may arise that nobody thought about during the planning phase.
    The orginal plan is where you started from, but it doesn't need to be where you end up. Just make sure that you properly discuss changes
    and that everyone involved agrees and understands the changes.

1.5
The sprint review is about the code that was produced, about the work that was actually done. Does it work, does it do what it's supposed to do?
While the retrospective is about the work methods used to get the work done. Do we need to change how we work to be more efficient?

1.9
* Scrum should not be about reporting to a boss.
* Everyone involved in a scrum should work together, if a boss is present, they are there as a participant, not as a boss.
* 45 minutes is way too long, the people talking the most need to seriously cut down on how much they talk.
